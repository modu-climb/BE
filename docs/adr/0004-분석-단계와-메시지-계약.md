# ADR-0004 분석 실행 단계와 워커 메시지 계약 보완

- 상태: 제안
- 날짜: 2026-10-13

## 배경

기능 명세서의 워커 메시지 계약을 도메인 설계에 맞춰 보니 아래 문제가 있다.

1. 메시지의 `attemptNo`(작업 재실행 회차)가 등반 시도 번호 `Attempt.attemptNo`와 이름이 같다.
2. `phase` 값이 `PHASE_2`처럼 번호뿐이고, 예시의 `PHASE_2`가 실제로는 분석(P4\~P7) 결과를 담고 있어 상태 머신의 세 단계와 맞지 않는다.
3. 재시도(같은 문제)라도 새 영상은 P0·P1을 거쳐야 하고, 촬영 위치가 정말 같은지 확인해야 한다.
4. 누락 홀드 탭(FR-07)은 사용자가 1초 안팎의 응답을 기대하는데, `analysis.jobs`에는 몇 분짜리 작업이 앞에 있을 수 있다.

## 결정

### 실행 단계

| 단계 (`phase`) | 파이프라인 | 작업 상태 | 주요 입력 | 주요 출력 |
| --- | --- | --- | --- | --- |
| `PREPROCESS` | P0\~P2 | `PREPROCESSING` | `videoKey`, 재시도면 기존 `wallSceneKey` | 반려 사유 또는 벽 기준 이미지·홀드 목록, `sceneMatched` |
| `INFER_PROBLEM` | P3 | `INFERRING_PROBLEM` | 기준 홀드 ID | 홀드별 소속 확률·상태, 역할 추정 |
| `ANALYZE` | P4\~P7 | `ANALYZING` | 문제 홀드 ID, 신체 스냅샷 | 산출물 키, 리포트, 모델 식별자 |

- 벽 깊이(P5의 벽 부분)는 새 촬영 위치일 때 `PREPROCESS`에서 미리 계산해도 된다. 백엔드는 산출물 키만 받는다.
- `PREPROCESS`의 `sceneMatched`가 `false`면 재시도라도 새 촬영 위치로 처리한다.

### 메시지 필드

- 작업 재실행 회차는 **`runNo`**(1부터)로 부른다. 이벤트 중복 제거 키는 `(jobId, phase, runNo)`다.
- 모든 메시지에 `schemaVersion`을 넣는다. 스키마는 `contracts/` 디렉터리의 JSON Schema 파일로 관리하고(M4의 4.1), 양쪽 테스트에서 검증한다.
- 큰 데이터는 지금처럼 스토리지 키로만 넘긴다.

```json
{
  "schemaVersion": 1,
  "type": "RUN_PHASE",
  "jobId": "0192...",
  "phase": "ANALYZE",
  "runNo": 1,
  "input": {
    "videoKey": "videos/2026/10/0192....mp4",
    "wallSceneKey": "scenes/0192.../",
    "problemHoldIds": ["h03", "h07", "h12"],
    "bodySnapshot": { "heightCm": 172, "wingspanCm": 176 }
  },
  "pipelineVersion": "0.3.0"
}
```

### 누락 홀드 탭 (FR-07)

- 별도 스트림 `analysis.interactive`로 보낸다. 워커는 이 스트림을 `analysis.jobs`보다 먼저 확인한다.
- API는 요청을 받으면 `202 Accepted`와 요청 ID를 돌려주고, 결과(새 홀드 마스크)는 같은 작업의 SSE로 보낸다.
- 워커가 긴 작업을 처리하는 중이면 응답이 늦을 수 있다. MVP에서는 이를 감수하고 응답 시간을 측정한 뒤, 필요하면 대화형 전용 워커를 따로 둔다.

## 결과

- 좋아지는 점
  - 이름 충돌과 번호만 있는 단계 이름이 사라져 로그·코드를 읽기 쉽다.
  - 재시도 흐름이 상태 머신과 맞아떨어진다.
- 감수할 점
  - [기능 명세서](../02_기능_명세서.md) 8장(워커 메시지 계약)을 고쳐야 한다. AI 트랙과 합의한 뒤 반영한다.
